4. VIABILIDADE WGPU/WGSL — ANÁLISE HONESTA
------------------------------------------------------------------------------
4.1 REGRA INVIOLÁVEL (leis da casa, prevalecem sobre qualquer
otimização): CPU Rust = estado canônico. GPU = acelerador de matemática
ou pura observação. Nada de GPU sem EVIDÊNCIA de necessidade (regra de
promoção E0-E5: necessidade demonstrada + efeito reproduzível +
consumidor real). Crise muda política, nunca desativa o fallback CPU.

4.2 POR QUE GPU NÃO SE PAGA NO TICK ATUAL: com 24 clusters x 97D e
padrões 32x32 cacheados, cada kernel candidato tem microssegundos de
trabalho; o overhead de dispatch/staging/readback wgpu seria maior
que o ganho. GPU se paga com: milhares de unidades, mesma operação
sobre muitos elementos, reduções grandes, pairwise massivo. Hoje não
há nenhum desses volumes.

4.3 VIÁVEL AGORA (baixo risco, valor imediato):
- PILOTO DE VISUALIZAÇÃO CHLADNI (render WGSL): o Chladni gera
  padrões de placa vibrante — imagens por natureza. Um fragment
  shader renderizando a grade N x N como heatmap (por tick ou
  varredura de banda) é OBSERVAÇÃO PURA: não toca estado canônico,
  não entra no tick do organismo, não tem política. É o caminho de
  menor risco para validar toda a infraestrutura wgpu (contexto,
  adapter, buffers, pipelines) e entrega harmonia VISÍVEL ao dono.
- FUNDAÇÃO NO PLATFORM (trait + config): barato, deixa o caminho
  pronto e não obriga a usá-la. ComputeBackend com CPUBackend
  (referência) e WgpuBackend vazio; seção [gpu] default DESLIGADO.

4.4 VIÁVEL COM PREPARO (médio prazo, condicionado à medição):
- Kernels compute em lote (se população/grade crescerem): energia/
  norma/atividade por cluster (SoA staging), reservoir/HOTM batch,
  varredura de padrões Chladni para M frequências (experimentos
  offline), afinidade pairwise do grafo.
- Testes golden CPU<->GPU por kernel: max_abs_error/mean_abs_error
  com tolerância declarada; CPU permanece a referência.

4.5 NÃO VIÁVEL / ADIADO (não fazer):
- GPU dona do estado canônico (só com estratégia de versão madura;
  hoje: nunca).
- Terceiro backend (o legado tinha OpenCL+WGPU+Numba = duplicação;
  a árvore nova terá no máximo 2: CPU canônico + wgpu acelerador).
- SoA ClusterStore SEM o requisito de escala seria risco A/A sem
  recompensa; COM a diretriz de 30K (seção 4.8) vira pré-requisito
  estrutural, feito por refatoração bit-idêntica.
- Um shader por módulo cognitivo (kernel é acelerador matemático,
  nunca "o sistema" — o módulo cognitivo continua em Rust).
- Lua com qualquer acesso à GPU (leis duras ficam em Rust).
- Tokio no loop cognitivo.

4.6 DETERMINISMO (classes declaradas): CPU = BITWISE_DETERMINISTIC
(padrão atual, A/A). Kernels GPU = NUMERICALLY_STABLE com tolerância
golden declarada por kernel; GPU nunca é fonte canônica de verdade —
quem publica no TypedContext continua sendo o módulo Rust dono.

4.7 HARDWARE: RX580 (registrada na versão anterior deste arquivo).
wgpu abstrai o backend (Vulkan/DX12 conforme o adapter); regra: não
assumir backend pelo nome — registrar adapter, backend efetivo,
limits, features e suporte a timestamp queries no boot.

4.8 DIRETRIZ DE ESCALA DO DONO (2026-09-29) — o que muda no plano:
- NÚMEROS: boot com 1.200 clusters; teto de 30K (50x do boot,
  1250x sobre os 24 atuais). Horizontal = módulos em paralelo NA
  MESMA máquina (alta-concorrência interna). Vertical = SoA + SIMD
  + WGPU. Clusters + HOTM existem para o sistema PENSAR — e pensar
  exige CADEIA COMPLETA com RECURSÃO (como no legado), não HOTM
  isolado.
- IMPLICAÇÕES (todas com as leis da casa preservadas):
  a) SoA n x 97 contínuo deixa de ser opcional: 30K objetos AoS
     destroem cache locality; refatoração bit-idêntica (A/A verde
     antes e depois).
  b) O lock global Arc<Mutex<L1Runner>> serializa o passo inteiro.
     A física por cluster paraleliza com rayon par_chunks e redução
     de ordem CANÔNICA (chunks fixos) — paralelismo sem quebrar o
     determinismo bit-exato.
  c) Concorrência interna de módulos: o scheduler do runtime executa
     módulos independentes em paralelo com barreira por passo e ordem
     de eventos determinística; budget e leis intocados.
  d) RECURSÃO COGNITIVA (fechar o loop, como no legado): atenção L3
     consumindo l1.substrate.chladni com peso [chladni].
     attention_weight; banda -> estágio no development (legado
     development.py). O sinal já está publicado; falta o consumidor
     ativo. ADR com experimento A/A antes de ativar o peso — a
     diretriz do dono está dada; a promoção continua exigindo
     evidência reproduzível (E0-E5).
  e) GPU: a 30K, os kernels batch (energia/norma por cluster,
     pairwise do grafo, reservoir) têm workload real. GO/NO-GO por
     kernel pelos benchmarks da fase 0, agora com carga sintética
     1.200 / 5K / 30K.
- ORDEM DE EXECUÇÃO (medição antes de otimizar, sempre):
  14.1 benchmarks baseline -> 14.2 SoA -> 14.3 paralelismo
  determinístico da física -> 14.4 concorrência de módulos ->
  14.5 recursão Chladni na cognição -> 14.6 carga 30K -> 14.7 GPU
  (se GO) -> 14.8 verificação final.

5. ARQUITETURA ALVO (SE promovido)
------------------------------------------------------------------------------
- Crate triad-gpu dentro de crates/platform/ (GPU fica no platform).
  Módulos: context (GpuContext persistente: instance/adapter/device/
  queue/pipelines/arena — criado UMA vez por run, nunca por step),
  backend (trait ComputeBackend + Cpu/Wgpu), shaders WGSL organizados
  por domínio (common/, substrate/, visualization/).
- Config central: seção [gpu] no config/default.toml — enabled=false
  por default; injeção por construtor (padrão dos pilotos [l1.survival]
  e [chladni]); adapter ausente = FALLBACK qualificado com
  provider_id + reason (nunca silêncio, nunca zero fantasma).
- Instrumentação: spans separados prepare/submit/wait/readback;
  timestamp queries quando suportadas; host_ms nunca confundido com
  kernel_ms; estatísticas com denominador (dispatches, hits de
  pipeline cache, bytes de staging).
- Boot: detect adapter -> log backend efetivo -> se indisponível,
  FALLBACK CPU explícito -> organismo segue idêntico.

7. REGRAS DA CASA APLICADAS (não negociáveis)
------------------------------------------------------------------------------
- CPU Rust canônico; GPU = acelerador/observação; fallback CPU
  sempre disponível e testado.
- Promoção por evidência: benchmark -> threshold -> ADR -> piloto ->
  golden -> produção. Nunca o contrário.
- Ausência != zero: adapter ausente = FALLBACK com provider + reason.
- Taxas sempre com denominador (incluindo estatísticas de dispatch).
- Leis duras em Rust; Lua sem acesso à GPU, sem RNG livre.
- Determinismo: CPU bit-exato (A/A preservado); tolerância GPU
  declarada por kernel em teste golden.
- Este arquivo é análise e plano; doc/ de arquitetura segue intocado
  (este arquivo foi reescrito por ordem direta do dono).
